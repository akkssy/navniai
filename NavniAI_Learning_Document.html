🔑 Key Design Decision

The workflow execution engine runs client-side in the browser. This eliminates server costs for long-running pipelines, gives users real-time streaming feedback per step, and simplifies deployment to static hosting. 2. Multi-Provider LLM System

NavniAI supports 6 LLM providers through a centralized registry pattern. Each provider is defined as a configuration object; the runtime resolves which provider to use based on user settings and availability.

Provider Registry Pattern

The registry maps provider keys to their configuration — endpoint format, required API key, header construction, and response parsing:

// lib/llmProviders.ts — Provider Registry (simplified)

export const PROVIDER_REGISTRY: Record<LLMProviderKey, ProviderConfig> = {
  ollama: {
    name: 'Ollama (Local)',
    requiresApiKey: false,
    defaultModel: 'llama3',
    buildEndpoint: (settings) =>
      `${settings.ollamaBaseUrl || 'http://localhost:11434'}/api/chat`,
    buildHeaders: () => ({ 'Content-Type': 'application/json' }),
    buildBody: (model, messages) => ({
      model,
      messages,
      stream: false,
    }),
    parseResponse: (data) => data.message?.content || '',
  },

  openai: {
    name: 'OpenAI',
    requiresApiKey: true,
    defaultModel: 'gpt-4o-mini',
    buildEndpoint: () => 'https://api.openai.com/v1/chat/completions',
    buildHeaders: (settings) => ({
      'Content-Type': 'application/json',
      Authorization: `Bearer ${settings.openaiApiKey}`,
    }),
    buildBody: (model, messages) => ({
      model,
      messages,
      max_tokens: 4096,
    }),
    parseResponse: (data) =>
      data.choices?.[0]?.message?.content || '',
  },

  // gemini, anthropic, groq, openrouter follow same pattern...
}
💡 AI Concept: Provider Abstraction

Each LLM API has a different request/response format. The registry pattern normalizes these differences behind a uniform interface — buildEndpoint, buildHeaders, buildBody, parseResponse — so the rest of the application doesn't need to know which provider is active.

Fallback Chain

When the primary provider fails, NavniAI cascades through alternatives automatically:

// lib/llmProviders.ts — Fallback execution

export async function callLLMWithFallback(
  prompt: string,
  settings: LLMSettings
): Promise<{ content: string; provider: string }> {

  // Build ordered provider list: [primary, ...fallbacks]
  const providers = [settings.provider]
  const fallbackOrder: LLMProviderKey[] =
    ['groq', 'openai', 'gemini', 'anthropic', 'openrouter', 'ollama']

  for (const fb of fallbackOrder) {
    if (fb !== settings.provider) providers.push(fb)
  }

  for (const providerKey of providers) {
    const config = PROVIDER_REGISTRY[providerKey]
    if (config.requiresApiKey && !getApiKey(settings, providerKey)) {
      continue // Skip providers without configured keys
    }

    try {
      const response = await fetch(
        config.buildEndpoint(settings),
        {
          method: 'POST',
          headers: config.buildHeaders(settings),
          body: JSON.stringify(
            config.buildBody(
              settings[`${providerKey}Model`] || config.defaultModel,
              [{ role: 'user', content: prompt }]
            )
          ),
        }
      )

      if (!response.ok) throw new Error(`${response.status}`)
      const data = await response.json()
      return {
        content: config.parseResponse(data),
        provider: providerKey,
      }
    } catch (err) {
      console.warn(`Provider ${providerKey} failed, trying next...`)
    }
  }

  throw new Error('All LLM providers failed')
}
✅ Resilience Pattern

The fallback chain ensures the application never breaks due to a single provider outage. If Ollama is offline, it tries Groq → OpenAI → Gemini → etc. The user sees which provider actually served the response via a badge in the output panel.

Retry with Exponential Backoff New in v2

Each provider in the fallback chain now retries with increasing delays before moving to the next provider — preventing transient errors from wasting the entire fallback budget:

// lib/llmProviders.ts — withRetry helper

async function withRetry<T>(
  fn: () => Promise<T>,
  maxAttempts: number,
  signal?: AbortSignal,
): Promise<T> {
  let lastError: unknown
  for (let attempt = 0; attempt < maxAttempts; attempt++) {
    if (signal?.aborted) throw new DOMException('Aborted', 'AbortError')
    try {
      return await fn()
    } catch (err) {
      // Never retry an abort — propagate immediately
      if (err instanceof DOMException && err.name === 'AbortError') throw err
      lastError = err
      if (attempt < maxAttempts - 1) {
        // Exponential backoff: 1s, 2s, 4s...
        await new Promise(r => setTimeout(r, 1000 * Math.pow(2, attempt)))
      }
    }
  }
  throw lastError
}
💡 AI Concept: Exponential Backoff

When a service fails, retrying immediately often makes things worse (thundering herd). Exponential backoff spaces retries: attempt 1 waits 1 s, attempt 2 waits 2 s, attempt 3 waits 4 s. This gives overloaded services time to recover. The key exception: AbortError is never retried — user intent to cancel is always respected immediately.

AbortSignal — Unified Cancellation New in v2

Every LLM call now accepts an AbortSignal. A makeSignal helper combines the user's cancel signal with a timeout signal, so whichever fires first wins:

// lib/llmProviders.ts — Combining timeout + user abort

function makeSignal(timeoutMs: number, userSignal?: AbortSignal): AbortSignal {
  const timeoutSignal = AbortSignal.timeout(timeoutMs)
  if (!userSignal) return timeoutSignal
  // AbortSignal.any — fires when EITHER signal aborts
  if (typeof AbortSignal.any === 'function') {
    return AbortSignal.any([timeoutSignal, userSignal])
  }
  // Polyfill for environments without AbortSignal.any
  const controller = new AbortController()
  const abort = () => controller.abort()
  timeoutSignal.addEventListener('abort', abort, { once: true })
  userSignal.addEventListener('abort', abort, { once: true })
  return controller.signal
}

// LLMCallOptions — the unified options object
export interface LLMCallOptions {
  settings?: LLMSettings
  timeoutMs?: number
  signal?: AbortSignal  // User-initiated cancel
  maxRetries?: number   // Retries per provider (default: 1)
}

Settings Persistence

Provider settings (API keys, model names, base URLs) are stored in localStorage and loaded via loadSettings(). This keeps sensitive keys client-side only — they never touch the server.

3. 3-Tier RAG Implementation

Retrieval-Augmented Generation (RAG) enhances LLM responses by injecting relevant context from a knowledge base into the prompt. NavniAI implements a 3-tier embedding strategy that balances cost, privacy, and availability.

What is RAG?

🧠 AI Concept: Retrieval-Augmented Generation

LLMs have a knowledge cutoff and no access to your private data. RAG solves this by: (1) converting documents into vector embeddings, (2) storing them in a vector database, (3) at query time, finding the most similar chunks and injecting them into the LLM prompt as context. The LLM then generates answers grounded in your actual data.

3-Tier Embedding Strategy

Tier 1 LocalOllamanomic-embed-text (768d)Default — free, private, no API key needed
Tier 2 CloudGoogle Geminitext-embedding-004 (768d)Fallback if Ollama unavailable

// lib/embeddings.ts — 3-Tier embedding generation

export async function generateEmbedding(
  text: string,
  options: EmbeddingOptions = {}
): Promise<EmbeddingResult> {
  const provider = options.preferredProvider || 'ollama'

  // Tier 1: Try Ollama (local)
  if (provider === 'ollama' || !options.geminiApiKey) {
    try {
      const baseUrl = options.ollamaBaseUrl || 'http://localhost:11434'
      const res = await fetch(`${baseUrl}/api/embeddings`, {
        method: 'POST',
        headers: { 'Content-Type': 'application/json' },
        body: JSON.stringify({
          model: 'nomic-embed-text',
          prompt: text,
        }),
      })
      if (res.ok) {
        const data = await res.json()
        return {
          embedding: data.embedding,
          provider: 'ollama',
          model: 'nomic-embed-text',
        }
      }
    } catch { /* Ollama unavailable, fall through */ }
  }

  // Tier 2: Try Gemini cloud API
  if (options.geminiApiKey) {
    try {
      const res = await fetch(
        `https://generativelanguage.googleapis.com/v1beta/models/` +
        `text-embedding-004:embedContent?key=${options.geminiApiKey}`,
        {
          method: 'POST',
          headers: { 'Content-Type': 'application/json' },
          body: JSON.stringify({
            model: 'models/text-embedding-004',
            content: { parts: [{ text }] },
          }),
        }
      )
      if (res.ok) {
        const data = await res.json()
        return {
          embedding: data.embedding.values,
          provider: 'gemini',
          model: 'text-embedding-004',
        }
      }
    } catch { /* Gemini failed, fall through */ }
  }

  // Tier 3: Browser-based fallback (768-dim random)
  // In production, this would use transformers.js
  const fallback = new Array(EMBEDDING_DIM).fill(0).map(
    () => Math.random() * 2 - 1
  )
  return {
    embedding: fallback,
    provider: 'browser-fallback',
    model: 'random-768',
  }
}

Text Chunking

Before embedding, documents are split into overlapping chunks to fit within model context windows and improve retrieval granularity:

// lib/embeddings.ts — Smart text chunking

export function chunkText(
  text: string,
  maxChunkSize: number = 500,
  overlap: number = 50
): string[] {
  const sentences = text.split(/(?<=[.!?])\s+/)
  const chunks: string[] = []
  let current = ''

  for (const sentence of sentences) {
    if ((current + ' ' + sentence).length > maxChunkSize && current) {
      chunks.push(current.trim())
      // Keep overlap from end of previous chunk
      const words = current.split(' ')
      current = words.slice(-Math.ceil(overlap / 5)).join(' ')
    }
    current += (current ? ' ' : '') + sentence
  }
  if (current.trim()) chunks.push(current.trim())
  return chunks
}
💡 Why Overlapping Chunks?

Overlap ensures that concepts spanning chunk boundaries aren't lost. If a key sentence sits at the end of chunk N, it's also captured at the start of chunk N+1, so the retrieval query can find it regardless of which chunk it matches.

Vector Similarity Search

At query time, the search endpoint generates an embedding for the user's query, then uses PostgreSQL's <=> operator (cosine distance) to find the most similar document chunks:

// app/api/rag/search/route.ts — Cosine similarity search

const results = await prisma.$queryRawUnsafe(`
  SELECT
    c.id, c.content, c."chunkIndex", c.metadata,
    d.name as "documentName",
    1 - (c.embedding <=> $1::vector) as similarity
  FROM "DocumentChunk" c
  JOIN "Document" d ON d.id = c."documentId"
  WHERE d."userId" = $2
  ORDER BY c.embedding <=> $1::vector
  LIMIT $3
`, vectorStr, userId, topK)
🧠 AI Concept: Cosine Similarity

Cosine similarity measures the angle between two vectors. A value of 1.0 = identical direction (semantically identical), 0.0 = orthogonal (unrelated). The <=> operator in pgvector computes cosine distance (1 - similarity), so we sort ascending and convert back with 1 - distance.

4. Visual Workflow Engine (+ Parallel, Branching, Cancel)

The heart of NavniAI is a client-side execution engine that processes directed graphs of AI agents. In v2 it gained parallel execution, conditional branching, cancellation, and the ReAct tool loop — making it a true orchestrator, not just a sequential runner.

Parallel Branch Execution New in v2

The executor finds all steps whose dependencies are satisfied each iteration and runs them concurrently with Promise.all:

// lib/workflowExecutor.ts — Parallel execution core loop (simplified)

while (remaining.length > 0) {
  if (payload.signal?.aborted) return { status: 'cancelled', ... }

  // Find ALL steps whose dependencies are already done
  const readyIndices = remaining
    .map((s, i) => i)
    .filter(i => remaining[i].depends_on.every(
      d => completed.has(d) || skipped.has(d)
    ))

  const readySteps = /* splice them out of remaining */ ...

  // Evaluate conditions — skip steps whose condition is false
  const stepsToRun = readySteps.filter(step => {
    if (!evaluateCondition(step.condition, outputs)) {
      skipped.add(step.id)
      outputs[step.id] = { status: 'skipped', output: '', provider: 'none' }
      return false
    }
    return true
  })

  // Sequential if HITL is active (user must review each step)
  // Parallel otherwise — independent branches run concurrently
  if (onCheckpoint) {
    for (const step of stepsToRun) await executeOneStep(step, ...)
  } else if (stepsToRun.length === 1) {
    await executeOneStep(stepsToRun[0], ...)
  } else {
    await Promise.all(stepsToRun.map(step => executeOneStep(step, ...)))
  }
}
💡 AI Concept: DAG Execution + Parallelism

A Directed Acyclic Graph (DAG) lets us find all steps whose inputs are already available and run them at the same time. This is the same pattern used by Apache Airflow, GitHub Actions, and Temporal. For example, in a content pipeline, SEO Optimizer and Social Writer can both run in parallel once the Writer finishes — halving wall-clock time.

Conditional Branching New in v2

Each workflow step can carry a condition string. If it evaluates to false, the step is skipped and downstream steps see it as completed:

// lib/workflowExecutor.ts — Safe condition evaluator

function evaluateCondition(
  condition: string | null,
  outputs: Record<string, any>
): boolean {
  if (!condition || !condition.trim()) return true  // no condition = always run
  try {
    let resolved = condition
    // Substitute {{stepId.status}} and {{stepId.output}} template vars
    for (const [sid, sd] of Object.entries(outputs)) {
      resolved = resolved
        .replace(`{{${sid}.status}}`, JSON.stringify((sd as any).status || 'completed'))
        .replace(`{{${sid}.output}}`, JSON.stringify(
          ((sd as any).output || '').slice(0, 500)  // truncate for safety
        ))
    }
    // Safe evaluation — no DOM access, no side effects
    // eslint-disable-next-line no-new-func
    return Boolean(new Function('"use strict"; return (' + resolved + ')')())
  } catch {
    return true  // If condition errors, default to running the step
  }
}

// Example condition in a workflow node:
// condition: "{{step_reviewer.status}} === 'completed'"
// condition: "{{step_researcher.output}}.includes('approved')"

Workflow Cancellation (AbortController) New in v2

Every run creates an AbortController. Its signal threads through the entire call stack — executor → LLM fallback chain → fetch() calls — so cancellation is immediate and clean:

// components/WorkflowBuilder.tsx — Cancel button wires up the ref
const abortControllerRef = useRef<AbortController | null>(null)

async function runPipeline() {
  const abortController = new AbortController()
  abortControllerRef.current = abortController
  setIsRunning(true)

  try {
    const result = await executeWorkflowClientSide(
      { workflow, inputs: {}, signal: abortController.signal },
      onProgress, onStream, onCheckpoint
    )
  } catch (err) {
    if (err?.name === 'AbortError') {
      setRunResult({ status: 'warning', message: 'Workflow cancelled by user' })
    }
  } finally {
    setIsRunning(false)
    abortControllerRef.current = null
  }
}

Human-in-the-Loop (HITL) Checkpoint

When a user enables review mode, execution pauses after each step and waits for the user to Approve, Edit, or Regenerate before continuing:

// lib/workflowExecutor.ts — HITL pause loop

if (onCheckpoint && remaining.length > 0) {
  let approved = false
  while (!approved) {
    if (payload.signal?.aborted) break     // respect cancel even during review

    onProgress?.({ status: 'reviewing', ... })

    const decision = await onCheckpoint({
      stepId, agentId, agentName, output, provider, stepIndex, totalSteps
    })

    if (decision.action === 'approve') {
      approved = true
    } else if (decision.action === 'edit') {
      output = decision.editedOutput || output
      structured = parseAgentOutput(step.agent, output)
      approved = true
    } else if (decision.action === 'regenerate') {
      // Re-run the full LLM call (including ReAct loop if tools enabled)
      const result = await callStepLLM(step, outputs, payload, onStream, scratchpad)
      output = result.output
      // Loop back — show the new output for review
    }
  }
}

Structured Handoffs Between Agents

Instead of passing raw LLM text between steps, NavniAI parses each output into typed fields and rebuilds a focused context string for the next agent:

// lib/agentOutputParser.ts — Field-level handoff
// Agent outputs use ===SECTION=== delimiters, which get parsed into:
// { title, keywords, summary, topics, mainContent, ... }

// buildHandoffContext converts structured output back to a clean prompt:
export function buildHandoffContext(structured: AgentStructuredOutput): string {
  if (!structured) return ''
  const parts: string[] = []
  if (structured.title)    parts.push('Title: ' + structured.title)
  if (structured.keywords) parts.push('Keywords: ' + structured.keywords.join(', '))
  if (structured.summary)  parts.push('Summary:\n' + structured.summary)
  // ...etc
  return parts.join('\n\n')
  // Benefit: next agent gets clean structured data instead of raw token soup
}

6. ReAct Tool-Use Loop & Agent Intelligence New in v2

In v1, agents were "prompt in → text out" boxes. In v2, they can reason about what tool to call, invoke it, observe the result, and continue reasoning until they have enough information. This is the ReAct (Reasoning + Acting) pattern.

🧠 AI Concept: ReAct Pattern

ReAct interleaves chain-of-thought reasoning with tool actions. The LLM outputs a Thought (what do I need?), then an Action (call this tool with these arguments), receives an Observation (the tool's result), and reasons again. This loop continues until the LLM outputs a Final Answer. It's the basis of systems like LangChain Agents and OpenAI's tool_use.

  systemPrompt: string,
  initialPrompt: string,
  step: WorkflowStep,
  payload: WorkflowPayload,
  scratchpad: Map<string, string>,
  onStream?: OnStreamCallback,
): Promise<{ text: string; provider: string; toolsUsed: ToolResult[] }> {

  const maxTurns = payload.maxReActTurns ?? 5
  let conversation = initialPrompt
  const toolsUsed: ToolResult[] = []

  for (let turn = 0; turn < maxTurns; turn++) {
    if (payload.signal?.aborted) throw new DOMException('Aborted', 'AbortError')

    // 1. LLM generates Thought + (optionally) ACTION calls
    const { text, provider } = await callLLMOnce(systemPrompt, conversation, ...)

    // 2. If LLM gave FINAL ANSWER — extract and return it
    if (hasFinalAnswer(text)) return { text: extractFinalAnswer(text), ... }

    // 3. Parse all ACTION: tool_name({...}) calls
    const toolCalls = parseToolCalls(text)
    if (toolCalls.length === 0) return { text, provider, toolsUsed }

    // 4. Execute each tool, collect OBSERVATION
    let observations = ''
    for (const call of toolCalls) {
      const result = await executeTool(call, scratchpad)
      toolsUsed.push(result)
      observations += `\nOBSERVATION [${call.tool}]: ${result.output}\n`
      // Stream the tool result to the UI with a 🔧 marker
      onStream?.(step.id, step.agent, `\n\n🔧 Tool: ${call.tool}\n${result.output}`, ...)
    }

    // 5. Append the exchange and loop back
    conversation += '\n\n' + text + observations + '\nContinue. Use FINAL ANSWER: when ready.'
  }

  // Max turns reached — force a final answer
  conversation += '\n\nProvide your FINAL ANSWER now.'
  const final = await callLLMOnce(systemPrompt, conversation, ...)
  return { text: extractFinalAnswer(final.text), provider: final.provider, toolsUsed }
}

💡 AI Concept: LLM-as-Judge

Using one LLM call to evaluate the output of another is called "LLM-as-Judge." It's surprisingly effective at catching shallow, incomplete, or off-topic outputs — especially for structured tasks. The key risk is that the judge can share the same biases as the generator. A production system would use a different model family for the judge to minimize this.

💡 Design: Prompt Augmentation vs. Native Function Calling

NavniAI's tools work via prompt augmentation — the tool result is injected as text into the LLM's conversation. This is provider-agnostic (works with Ollama, Groq, any model). Native function calling (OpenAI tool_use, Anthropic tool_use) is faster and more reliable when available, but locks you to specific providers. The prompt-based approach trades some reliability for universal compatibility.

9. Authentication & Middleware

NavniAI uses NextAuth.js with a Credentials provider for email/password authentication, backed by bcrypt hashing and Prisma for user storage.

Auth Configuration

// lib/auth.ts — NextAuth configuration

export const authOptions: NextAuthOptions = {
  providers: [
    CredentialsProvider({
      name: 'credentials',
      credentials: {
        email: { label: 'Email', type: 'email' },
        password: { label: 'Password', type: 'password' },
      },
      async authorize(credentials) {
        if (!credentials?.email || !credentials?.password) return null

        const user = await prisma.user.findUnique({
          where: { email: credentials.email },
        })
        if (!user?.password) return null

        const isValid = await bcrypt.compare(
          credentials.password,
          user.password
        )
        if (!isValid) return null

        return { id: user.id, email: user.email, name: user.name }
      },
    }),
  ],
  session: { strategy: 'jwt' },
  callbacks: {
    async jwt({ token, user }) {
      if (user) token.id = user.id
      return token
    },
    async session({ session, token }) {
      if (session.user) (session.user as any).id = token.id
      return session
    },
  },
}

🧠 AI Concept: Vector Databases

Traditional databases search by exact match or range. Vector databases enable semantic search — finding records by meaning, not keywords. The vector(768) column stores 768-dimensional float arrays. pgvector adds index types (IVFFlat, HNSW) and distance operators (<=> cosine, <-> L2) to PostgreSQL.

Prisma + pgvector Integration

Since Prisma doesn't natively support the vector type, NavniAI uses Unsupported("vector(768)") in the schema and raw SQL for insert/query operations:

13. AI Concepts Glossary

A reference of all AI and software architecture concepts implemented in NavniAI.

Large Language Models (LLMs)

Neural networks trained on vast text corpora that generate human-like text. NavniAI uses them as the "brain" inside each agent. Different providers (OpenAI, Anthropic, etc.) offer different models with varying capabilities, speed, and cost trade-offs.

Embeddings

Dense vector representations of text where semantically similar texts have vectors pointing in similar directions. NavniAI uses 768-dimensional embeddings. The number 768 was chosen because it's the output dimension of both nomic-embed-text (Ollama) and text-embedding-004 (Gemini), ensuring vector compatibility across tiers.

Cosine Similarity

Measures the angle between two vectors, producing a score from -1 to 1. In practice, embedding vectors are usually positive, so scores range 0 to 1. NavniAI uses this to find the most relevant document chunks for a given query.

// Cosine similarity formula:
// similarity = (A · B) / (||A|| × ||B||)
//
// pgvector operator: <=> returns cosine distance (1 - similarity)
// So: similarity = 1 - (embedding <=> query_vector)

Retrieval-Augmented Generation (RAG)

A pattern that combines information retrieval with text generation. Instead of relying solely on the LLM's training data, RAG fetches relevant context from a database at query time and includes it in the prompt. This grounds the LLM's response in actual data, reducing hallucinations.

Prompt Engineering

The practice of crafting effective prompts to get desired behavior from LLMs. In NavniAI, each agent has a system prompt defining its role, and the workflow executor constructs user prompts by combining action templates, resolved input variables, and optional RAG context.

Multi-Agent Orchestration

Running multiple specialized AI agents in a coordinated pipeline. Each agent handles one task, and outputs flow to the next agent. This is more effective than a single general-purpose prompt because: (1) each prompt is focused and shorter, (2) the system is modular, and (3) different steps can use different models or providers.

Directed Acyclic Graphs (DAGs)

A graph with directed edges and no cycles. NavniAI workflows are DAGs — each edge goes from one node to another (directed), and you can't create loops (acyclic). Topological sorting of a DAG produces a linear execution order where every dependency is satisfied before execution.

Provider Fallback / Circuit Breaker

A resilience pattern where if the primary service fails, the system automatically tries alternatives. NavniAI's callLLMWithFallback implements this by iterating through configured providers until one succeeds. This ensures the application degrades gracefully instead of failing completely.

Vector Database Indexing

pgvector supports two index types for approximate nearest neighbor (ANN) search:

  • IVFFlat: Inverted file index — partitions vectors into clusters, searches only nearby clusters. Fast to build, good for medium datasets.
  • HNSW: Hierarchical navigable small world — graph-based index with better recall. Slower to build but faster at query time for large datasets.

CSS Variable Theming

A pattern where colors are defined as CSS custom properties (--surface-300) instead of hardcoded values. By toggling a class on the root element (.dark), all colors switch simultaneously. Combined with Tailwind's rgb(var() / <alpha-value>) syntax, this enables full opacity control with theme-aware colors.

Hydration

In server-rendered React (Next.js), the server generates HTML, and the client "hydrates" it by attaching event handlers. If the server HTML differs from what the client would render (e.g., theme class mismatch), React throws a hydration error. suppressHydrationWarning tells React to ignore this specific mismatch.

ReAct (Reasoning + Acting) v2

A prompting strategy where the LLM alternates between generating reasoning traces (Thought) and executable actions (Action). After executing an action, the result (Observation) is fed back to the LLM, which reasons again. This loop continues until the LLM produces a Final Answer. ReAct agents are significantly more capable than single-turn prompting because they can gather, verify, and synthesize information across multiple tool calls.

Tool Use / Function Calling v2

Giving LLMs the ability to invoke external functions (tools) during generation. NavniAI implements this via prompt augmentation — the tool list and usage format are injected into the system prompt, and the executor parses ACTION: tool_name({...}) markers from the LLM's output. Native function calling (OpenAI's tools, Anthropic's tool_use) is more structured but provider-specific. Prompt-based tool use works with any model.

Agent Memory v2

Agents need memory at three timescales: (1) In-context — the conversation history within one LLM call, limited by the model's context window. (2) Short-term — the shared scratchpad across all steps in one workflow run, implemented as a Map<string, string>. (3) Long-term — persisted entries in the AgentMemory PostgreSQL table, surviving across runs. NavniAI implements all three.

Self-Reflection / LLM-as-Judge v2

Using one LLM call to evaluate the quality of output produced by another. The "judge" scores the output on dimensions like completeness, accuracy, and relevance. If quality falls below a threshold, the system auto-retries with the judge's feedback injected as additional context. Risks: the judge may share the generator's biases; using a different model family for evaluation reduces this. In NavniAI, the same model judges its own output, which works as a lightweight quality gate but may miss deeper issues.

Exponential Backoff v2

A retry strategy where wait time doubles between attempts: 1 s → 2 s → 4 s. This prevents thundering herd — a surge of simultaneous retries that overwhelm a recovering service. NavniAI applies this per LLM provider before falling to the next provider in the fallback chain. AbortError is always propagated immediately, never retried.

AbortController / AbortSignal v2

A browser-native API for cancelling asynchronous operations. An AbortController creates a paired AbortSignal. Calling controller.abort() fires the signal's abort event, which all fetch() calls listening to that signal will immediately reject with DOMException('AbortError'). NavniAI threads the signal from the user's Cancel button all the way through the executor → LLM fallback chain → individual provider fetch calls, ensuring clean, immediate cancellation with no dangling requests.

Parallel Workflow Execution v2

When multiple workflow steps have all their dependencies satisfied at the same time (parallel branches), they can run concurrently with Promise.all. This halves wall-clock time for branching pipelines (e.g., SEO + Social steps running simultaneously after a Writer step). The executor falls back to sequential execution only when Human-in-the-Loop review is active, because the user must approve each step before the next begins.

Dual-Write Persistence v2

Writing the same data to two stores simultaneously: localStorage for instant offline access, and PostgreSQL for durability and cross-device availability. The dashboard reads from the API (DB) first and falls back to localStorage if the network is unavailable. This pattern provides both low latency (local) and reliability (remote) without requiring a service worker or offline-first framework.
